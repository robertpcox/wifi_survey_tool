# Coding pattern — optimize for agent reading cost

## Purpose

The limits exist so an agent can understand and change one concern without loading a monofile.
They are not formatting targets and must not be defeated with compressed or unusually long lines.

## Enforced limits

The default build fails when any authored file exceeds a review target.

| Measurement | Target | Hard ceiling |
|---|---:|---:|
| Physical lines | 150 | 400 |
| File bytes | 10,000 | 20,000 |
| Longest line bytes | 160 | 500 |

The first limit reached wins. Comments count toward every limit.

`node tools/check_file_sizes.mjs .` is strict and exits non-zero for review or ceiling breaches.
`--allow-review` is permitted only during the initial split and never permits a hard-ceiling breach.

The only project-content exclusions are directories named `data/` and `results/`.
Repository internals such as `.git/` are traversal exclusions, not project exceptions.

Test files are authored files and are measured like any other.
One test file per module, beside the module, never one file collecting a whole layer.
Layout rules are in `Scope/test_standard.md`.

Captures, definitions, results, and generated manifests therefore live under those directories.
An authored page must never embed a data blob to work around a limit.

## Navigation metadata

Authored files carry no boilerplate header block.
Navigation metadata is generated: `docs/module-map.md` is the single index of purpose,
exports, dependencies, and size, and it is regenerated by the build, not maintained by hand.

## Cohesion rules

- Split by reason to change, not by function count.
- A normal task should require reading one to three implementation files.
- Do not create one-function files unless the function is a stable domain boundary.
- A function targets 40 lines and must not exceed 70 lines without being split.
- Keep nesting shallow and name intermediate decisions.
- Do not compress code, templates, CSS, arrays, or objects to satisfy line limits.
- Large HTML fragments belong in focused templates or view modules.
- Large CSS belongs to page, component, or feature stylesheets.

## File extensions

Every JavaScript file is `.mjs`.

The repository has no `package.json`, so Node treats `.js` as CommonJS. Domain modules are
imported by both Node tests and the browser, so a single ESM-by-extension rule is what keeps
one file usable from both. `tools/check_file_sizes.mjs` already sets the precedent.

The cost lands at serving time. A static host must return a JavaScript content type for
`.mjs`, or the browser refuses to execute the module and the failure looks like a missing
file. The served Nginx configuration declares that mapping explicitly rather than relying on
the default `mime.types`, and Step 2 proves it against the real configuration.

The alternative, a dependency-free `package.json` declaring `type: module` so `.js` works
everywhere, is rejected because a manifest invites `npm install` into a repository whose
whole point is that nothing installs.

## Dependency direction

Dependencies flow in one direction:

```text
apps -> features -> domain -> shared
                         \-> adapters
```

- App modules compose features and own page boot only.
- Feature modules own one user-visible capability.
- Domain modules contain pure survey, route, result, and analysis logic.
- Adapters isolate maps, polling providers, storage, files, and browser APIs.
- Shared modules contain small, genuinely cross-cutting utilities.
- No app imports another app.
- No hidden globals or implicit cross-page state.
- Avoid broad barrel files; use explicit imports from the owning module.

## Data rules

- Large captures, generated manifests, survey definitions, and results live under `data/` or `results/`.
- Keep minimal fixtures for tests; do not make agents read full captures to discover a schema.
- Each data family has a short README describing shape, provenance, and safe sample commands.
- Secrets never appear in source, fixtures, generated manifests, definitions, results, or screenshots.

## Fan-out rules

- Freeze shared contracts before parallel implementation begins.
- Give each agent exclusive ownership of a feature directory or report section, tests included.
- Do not assign parallel agents changes to the same registry, shell, or shared module.
- Integrate through small documented interfaces and fixtures.
- Finish and validate a split before starting feature changes in the same files.
- Follow `Scope/step_standard.md` for downstream updates, handovers, logs, and respawn boundaries.

## Build gates

The zero-dependency Node build must check:

1. File lines, bytes, and longest-line bytes.
2. Import direction and forbidden cross-app imports.
3. Survey and result schema fixtures.
4. Generated survey, result, and customer manifests.
5. Unit tests using `node:test`.
6. A generated `docs/module-map.md` with paths, exports, imports, lines, and bytes.
7. The secret scan across source, fixtures, manifests, and generated output.

These are one command, not a checklist someone remembers to run.
Every gate and every test in `Scope/test_plan.md` runs as part of the build, and any failure
fails the build. No `dist/` is emitted from a failing build, so a broken artifact cannot be
deployed by accident.

Browser tests requiring Chrome run in the same command when Chrome is present and are
reported as skipped, never silently passed, when it is not.

Generated browser assets must remain readable. Minification is not part of the authored build.
